# Оценка уровня кода и рекомендации по росту

## Честная оценка уровня

**Итог: уровень сильного джуна / входа в мидл (0.5–1.5 года коммерческого опыта по ощущению кода).**

Это **не** "ноль опыта": у тебя есть цельный бэкенд на Spring Boot с безопасностью, бизнес-логикой, рекомендациями и покупками. Для дипломного/учебного проекта это **хороший уровень**. Для "6 лет опыта" этого недостаточно — и это нормально.

---

## Что уже хорошо

### Архитектура и стек
- **Слои**: контроллеры → сервисы → репозитории, DTO, мапперы (MapStruct), отдельные исключения и глобальный обработчик.
- **Стек**: Spring Boot 3, Java 17, JPA/Hibernate, Spring Security, JWT, Liquibase, PostgreSQL, валидация.
- **Сущности**: корректные связи (OneToMany, ManyToMany), LAZY, каскады, enum для типов корзин и статусов.

### Бизнес-логика
- **Покупки**: расчёт суммы, транзакция, списание баланса, сохранение покупок, очистка корзины — логика связная.
- **Рекомендации**: жанры по избранному, исключение купленных игр, разнообразие по жанрам, fallback на топ по рейтингу — уже не "учебная заглушка".
- **Репозитории**: пагинация, кастомные JPQL/native-запросы (рейтинги, рекомендации), учёт БД.

### Качество кода
- Lombok, `@RequiredArgsConstructor`, интерфейсы сервисов.
- В контроллерах — роли (`@PreAuthorize`), разделение по эндпоинтам.
- В сервисах — разбиение на приватные методы (например, в `BuyServiceImpl`).
- Есть юнит-тесты (например, `BuyServiceTest` с моками).

## Что исправить (баги и риски)

### 1. Баг в `addRating` (GameServiceImpl)

**Сейчас:** если рейтинга **ещё нет** (`!existsRatingByAccountAndGame`), выбрасывается "Your rating already exists".

**Нужно:** выбрасывать "already exists", когда рейтинг **уже есть**:

```java
if (gameRepository.existsRatingByAccountAndGame(accountId, gameId)) {
    throw new IllegalArgumentException("Your rating already exists and you cannot change it.");
}
```

То есть убрать отрицание `!`.

---

### 2. Несовпадение имени таблицы в `Game` (ManyToMany с Bucket)

**Сейчас:** в `Game.java` указано `name = "bucket_games"`, в БД и в `Bucket` — таблица `buckets_games`.

**Нужно:** в сущности `Game` в `@JoinTable` указать `name = "buckets_games"`, как в БД и в `Bucket`.

---

### 3. SecurityConfig — отключить debug в проде

**Сейчас:** `@EnableWebSecurity(debug = true)` — в проде это утечка информации.

**Нужно:** `debug = false` или вынести в `application.yml` (например, через свойство и `@Value`), чтобы в проде было выключено.

---

### 4. Глобальный обработчик исключений

**Сейчас:** `EntityNotFoundException` и подобные отдаются как **500 Internal Server Error**.

**Лучше:** для "сущность не найдена" возвращать **404 Not Found** (отдельный обработчик с `HttpStatus.NOT_FOUND`), 500 оставить для реальных сбоев.

---

### 5. N+1 в `BuyServiceImpl.savePurchases`

**Сейчас:** в цикле по играм вызывается `accountRepository.findById(ownerId)` — один и тот же аккаунт запрашивается много раз.

**Лучше:** один раз получить `Account` до цикла и использовать его во всех `Purchase`.

---

### 6. `BucketServiceImpl.getById`

**Сейчас:** используется устаревший `getById(id)` (JPA может вернуть прокси и дать LazyInitializationException при доступе к полям).

**Лучше:** использовать `findById(id).orElseThrow(() -> new BucketNotFoundException(id))`.

## Рекомендации: как расти как инженер

### 1. Углубить основы

- **SQL**: как работают индексы, EXPLAIN, почему N+1 бьёт по производительности; как писать один запрос вместо цикла.
- **Транзакции**: изоляция, распространение (`@Transactional(propagation = ...)`), когда делать rollback.
- **JPA**: когда LAZY кидает LazyInitializationException, как правильно делать join fetch / EntityGraph, разница между save и merge.

### 2. Качество и надёжность

- **Логирование**: структурированные логи (например, SLF4J + JSON), не логировать пароли и токены.
- **Тесты**: не только юнит-тесты сервисов, но и интеграционные (например, `@DataJpaTest`, `@WebMvcTest` или полный контекст с тестовой БД).
- **Валидация**: использовать `@Valid` и Bean Validation в DTO там, где ещё не используешь.

### 3. API и эксплуатация

- **REST**: для создания возвращать 201 Created и заголовок Location; для удаления — 204 No Content; единообразные форматы ошибок (код, сообщение, опционально поле).
- **Безопасность**: убрать debug в проде; понимать, что такое CSRF, зачем нужны роли и как не светить лишнее в ошибках.

### 4. Практика на работе / в пет-проектах

- Читать чужой код (опенсорс, ревью в команде).
- Рефакторить свой старый код: выносить дублирование, давать осмысленные имена, дробить большие методы.
- Один раз пройти от идеи до деплоя: Docker, CI (сборка + тесты), деплой на один сервер или в облако.

### 5. Как пользоваться помощью (в т.ч. ИИ)

- Присылать кусок кода + задачу + ошибку/ожидание — так можно точечно искать баги и оптимизировать запросы.
- Просить не "напиши за меня", а "объясни, почему так" и "что улучшить" — так растёт понимание.
- После подсказки пробовать сама применить то же в другом месте.
